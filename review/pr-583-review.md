# Review: PR #583 `ui/colour-system` (soft-blue accent, three button kinds, approval card restyle)

Reviewed `origin/main...origin/ui/colour-system` (3 commits, 39 files). Review only; nothing run (the PR itself says the ui-preview binary and `cargo test -p yantrik-ui` were never run).

## Summary
Security core is mostly sound: the approval card's Deny/Allow once are now `YButton`s with a new `pointer-only` flag that disables the inner FocusScope, so nothing is focused when the card appears, Tab cannot land on them, and Enter/Space cannot press them. Both still call `root.allow()` / `root.deny()`, which still reach `on_approval_allow` in `control_approvals.rs:1319`, where `card_watch::just_raised()` (the 700 ms press guard) is untouched. No Rust changed (`crates/yantrik-ui` has 0 diff lines). No new autofocus, FocusScope, key-pressed, `accepted` or `init` on the card (the existing `focus()` calls in intent_lens.slint are the chat inputs, unchanged). Red is used only for irreversible acts; Deny is not red. But `pointer-only` leaves a non-pointer press path open (accessibility default action), the new test would not catch a regression on the real card, and the accent change breaks the "teal for minds" and settings-swatch rules.

## Findings

### BLOCKER
1. **`pointer-only` does not stop the accessibility default action from pressing Allow once.** `crates/yantrik-ui-kit/slint/y_button.slint:41` (`accessible-action-default => { if (!root.disabled && !root.loading) { root.clicked(); } }`) is not gated on `pointer-only`. The component is `accessible-role: button`, so an AT-SPI client (screen reader, or any same-session process/mind with accessibility access doing DoDefaultAction) can press "Allow once" with no pointer and no keyboard. Previously the card's buttons were bare Rectangle+TouchArea with no accessible action, so this is a new path, and it contradicts the PR's own claim ("A click is the only way to answer", intent_lens.slint:681; report "Approval security properties"). The press guard still applies afterwards, but guard is only 700 ms after shell raise, so it is not a substitute. Fix: `if (!root.disabled && !root.loading && !root.pointer-only) { root.clicked(); }` (or a deliberate, documented decision to keep AT access, with a test and a reviewer sign-off from the security owner). Add the case to the test.

### SHOULD-FIX
2. **The new test does not guard the real card.** `tests/ui-preview/src/colour_system_tests.rs:60-70` and `colour_system_probe.slint:30-31` test a hand-built pair of YButtons, not `ApprovalCard`. Deleting `pointer-only: true` at `intent_lens.slint:690/698` would pass every check. Also, the keyboard loop only proves the property by accident: it sends Tab/Enter/Space four times, and focus starts at Delete (last clicked); without `pointer-only` it reaches Allow once only on the 2nd iteration. If probe order changes it can silently pass. Fix: drive `ApprovalCard` (there is `approval_tests.rs` / `verify-cards-waiting` scene to extend) and assert (a) no `has-focus` after show, (b) Tab/Enter/Space/Return never fire `allow`/`deny`, (c) a click does. Also add a `control_approvals.rs`-style source-scan test that the card's two buttons keep `pointer-only: true`.
3. **Settings accent swatch and names are now wrong.** `crates/yantrik-ui-slint/ui/settings.slint:746` still `{id:"cyan",label:"Cyan",color:#38d8cd}` (the comment above it says it must equal the preset's dark value and "drifted once already"); preset 0 is now `#8fb4e3`. Picker shows teal, applies blue. Also raw hex in a component (playbook: tokens not hex) and ids/labels `"cyan"` remain in `wire/settings.rs:15,92,454`, `app-runtime/src/theme.rs:29`. Fix: label "Soft blue", colour from a token, keep the serialised id for compatibility. Also `ThemeOverrides.accent-override: #38d8cd` (theme.slint:97) still defaults to the old teal.
4. **Teal-only-for-minds rule weakened.** The report admits every `Theme.accent` user (agents.slint 14 uses, settings 53, email 26 ...) is now blue, "including mind surfaces". Mind marks/state in Agents were previously coloured by accent (which was teal-cyan); spec says mind identity is teal. Fix: grep `Theme.accent` in agents.slint, intent_lens.slint (2), chat/mind surfaces and move mind identity to `Theme.cyan`; list what was audited in the report. Note `onboard_kit.slint:82,86,116` still use `Theme.cyan` for input focus/selection on non-mind first-run fields (pre-existing, teal used for non-mind).
5. **Email flagged state lost.** `crates/yantrik-ui-slint/ui/email.slint` star button: `variant: root.email-detail.is-flagged ? 1 : 1;` (was `? 1 : 2`). Flagged and unflagged now look identical. Fix: show state another way (accent icon tint when flagged, or `variant: is-flagged ? 0 : 1`), remove the dead ternary.
6. **One concern / blast radius.** 39 files mix: (a) accent re-hue, (b) button kinds, (c) the security-sensitive approval card, (d) selection restyle (list, taskbar, switcher), (e) a button-reuse consolidation (PillButton, FlatButton, snippet/spreadsheet delete). Playbook: one concern per PR; and the approval card change should be reviewable alone. Also ~80 mechanical `variant: 2` -> `1` edits turn every quiet toolbar/icon button (file browser tabs, close-X, terminal find, email icons) into a 1px outlined box, a visible density regression not shown in any screenshot (report: no PNG was looked at). Fix: split approval card + `pointer-only` into its own PR; at minimum keep icon-only close/nav buttons borderless via a defined kind rather than silently deleting the tertiary.
7. **Unverified claims in `review/ui-colour-system-report.md`.** It is honest that preview and `cargo test -p yantrik-ui` did not run, but then also states "Verified: cargo test -p yantrik-ui-kit: 7 passed" and "cargo check passes", while the PR touches security files' behaviour and playbook requires "look at the PNGs". Merge bar not met: the pixel assertions in `colour_system_tests.rs:55-62` (hard-coded dark-theme hex, 3-tolerance) and the approval test are unrun. Run `verify-colour-system`, `verify-cards-waiting`, `verify-kit-controls`, `verify-idle`, and `cargo test -p yantrik-ui --bin yantrik-ui` on a bigger machine before merge. Report also says "all call sites moved to 1": `tests/ui-preview/preview.slint:110-111` still `variant: 2`.
8. **Branch is behind main.** Merge base `4c9b898`; `origin/main` is 2 commits ahead and one touches `theme.slint`. Playbook requires rebase before merge.
9. **Other approval-like surfaces left inconsistent.** `AgentProposalCard` (`crates/yantrik-ui-kit/slint/agent_proposal.slint:~175`) "Apply" is a filled primary (or red) YButton that is keyboard-focusable and Enter/Space pressable (clicking sets focus; Tab reaches it). It is an agent-proposed change the person consents to; spec says approval buttons are never Enter-pressable. Not a regression (unchanged behaviour), but the PR claims a system and does not apply `pointer-only` there. Same for the card's third "Allow ... for this session" row (hand-built TouchArea, unchanged, still pointer only: fine). Decide explicitly and say so in the PR text.
