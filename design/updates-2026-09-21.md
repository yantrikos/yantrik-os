# One update path

2026-09-21. Yantrik OS had four programs with an opinion about how the machine updates itself,
and they disagreed. This is what each one actually did, what was wrong with it, and what the
single path is now.

Written so that the next person who asks "why did my machine not update" has one file to read
and one file to look at on the machine.

---

## 1. What there was

### a. `deploy/yantrik-os/yantrik-update` — the real one

A shell script installed at `/opt/yantrik/bin/yantrik-update`. `check | apply | rollback |
status`, `--channel C`. It reads the release manifest at
`https://releases.yantrikos.com/manifest.json`, whose shape is:

```json
{"channels": {"nightly": {"version","date","url","notes","git","artifact","sha256","binaries"}}}
```

It downloads the channel's `.tar.zst`, verifies it against the manifest's sha256, backs up the
current `bin/` and `share/`, swaps the new ones in, restarts the session through systemd, and
rolls back automatically if the new shell does not answer its control socket. This path was
sound and is the one everything now goes through.

### b. `crates/yantrik-ui/src/control_update.rs` — the control surface

Exposed `check_update` (safe) and `apply_update` (dangerous, deferred) by running that script
and reading its exit codes. Also sound. It was the model for the rest of this work.

### c. `crates/yantrik-ui/src/wire/version.rs` — a second checker, which could only lie

This backed the About screen's "Check for updates" button. It did not run the updater. It:

- fetched `http://releases.yantrikos.com/manifest.json` — **plain http, hardcoded**, regardless
  of what the machine was configured with;
- used the channel `"stable"` — **hardcoded**, regardless of the machine's channel;
- read `channels[ch]["components"][<crate name>]["version"]` — **a shape no manifest this
  project has ever published**. The manifest describes whole builds. There is no `components`
  key in it and there never was, so every lookup missed and `latest` fell back to the local
  version;
- and returned `components.map(no_update)` from **every** error path — DNS failure, refused
  connection, malformed JSON, all of them.

The consequence: the only sentence that screen could produce was *"All components up to
date."* On a machine with no network. On a machine on a channel that is not `stable`. Always.
A fabricated success, on the screen a person opens precisely when they suspect something is
stale.

### d. `updates:` in `config-default.yaml` — a setting nobody read

```yaml
updates:
  channel: "beta"
  server: "https://releases.yantrikos.com"
  check_on_boot: true
```

`grep -rn 'updates\.channel\|updates\.server\|check_on_boot' crates/` returns nothing. No Rust
crate has ever read any of those three keys. But `build-debian-iso.sh` *did* read
`updates.channel` with `sed`, to decide the channel it wrote into the image's `update.conf` —
so the one effect this dead setting had was to build the first public nightly ISO pointed at
`beta`, a channel whose newest build was six months older than the image itself.

## 2. Three answers to "which channel is this machine on"

Before:

| Source | Said | Present on |
| --- | --- | --- |
| `update.conf` `CHANNEL=` | whatever the image was built for | ISO installs, cloud-init machines |
| `config.yaml` `updates.channel` | `beta` | every machine — and read by nothing |
| `yantrik-update`'s own default | `stable` | every machine with no `update.conf` |
| `/opt/yantrik/BUILD` `channel=` | the channel `apply` last installed from | machines that had updated at least once |

A machine installed from a release bundle by a path that wrote no `update.conf` asked the
server for `stable`. Nothing has ever been published to `stable`. The answer it got was
*"cannot reach the release server or channel 'stable' is not published"* — one sentence for two
completely different problems, on a machine that was perfectly current.

**Correction to the brief:** the cloud-init path (`deploy/yantrik-os/cloud-init/user-data.yaml`)
*did* already write `update.conf`, deriving `CHANNEL` and `HOST` from the release URL. It did
not write `SCHEME`, so `boottest.py`'s assertion that an installed machine is on https could
only ever pass on ISO installs. And it derived those from a **plain-http** URL.

## 3. What it is now

**`/opt/yantrik/update.conf` is the single owner of channel, host and scheme.** One file, flat
`KEY=value`, read and written by exactly one program.

`yantrik-update` resolves the channel in this order, most specific first:

1. `CHANNEL` in `/opt/yantrik/update.conf`
2. `channel=` in `/opt/yantrik/BUILD` — the channel the installed build came from, recorded by
   `apply`
3. `CHANNEL_DEFAULT`, now `nightly`, with a comment saying it is the only published channel
   today and that changing that one line is the whole change when `stable` starts receiving
   builds

`status --porcelain` reports which of the three answered, as `channel_source=`. "The channel is
nightly" and "the channel is nightly because nobody has ever said otherwise" are different
facts, and the second is the one that explains a surprise.

`config.yaml` no longer carries an `updates:` section. A shell script cannot sanely parse YAML,
and the shell script is the thing that has to work at 3am on a machine with no desktop running,
so the flat file is the owner and the YAML stops having an opinion.

### Every path writes it

| Path | Channel comes from |
| --- | --- |
| `build-debian-iso.sh` | its own default `nightly`, overridable by `YANTRIK_UPDATE_CHANNEL` |
| `cloud-init/user-data.yaml` | the URL the bundle was installed from (now https, now with `SCHEME=`) |
| `yantrik-install.sh` | the image's own `update.conf`; if absent, `channel=` from `BUILD`, else `nightly` |
| `yantrik-update apply` | records `channel=` into `BUILD` as it installs |
| `yantrik-update set-channel` | the person, through the About screen or the command line |

### The bundle does not carry one

`build-release.sh` builds the tarball once, and `--publish` can send that same tarball to more
than one channel. A channel name inside it would be right for the first channel and a lie for
the rest — and a lie `yantrik-update` believes, since it falls back to `BUILD`'s `channel=`.
The thing that *downloads* the bundle knows which channel it came from, because it downloaded
it from a channel URL. So the downloader writes `update.conf`, and nothing guesses.

## 4. The script's new surface

```
yantrik-update check       [--channel C] [--porcelain]
yantrik-update apply       [--channel C] [--force] [--allow-downgrade] [--reboot] [--no-restart]
yantrik-update rollback
yantrik-update status      [--porcelain]
yantrik-update set-channel nightly|beta|stable
yantrik-update selftest
```

**Two output formats, on purpose.** Everything a person reads is the coloured prose. Everything
a *program* reads comes from `--porcelain`: one `key=value` per line, no colour, no sentence a
rewording breaks.

`check` exit codes: `0` up to date · `10` update available · `11` channel not published · `12`
server unreachable · `1` anything else. The porcelain `result=` line says the same thing in
words; both are emitted so neither has to be inferred from the other.

`check --porcelain`:

```
result=up_to_date|update_available|not_published|unreachable|error
channel=nightly
channel_source=update.conf|BUILD|default|--channel
host=releases.yantrikos.com
scheme=https
installed_version=0.4.2
installed_git=deadbee
channel_version=0.4.2
channel_git=deadbee
published=nightly            (only on not_published)
reason=<one sentence>
```

`status --porcelain`:

```
channel= channel_source= host= scheme= conf= conf_present=yes|no conf_writable=yes|no
version= git= name= installed= backups=
```

### Two faults fixed in passing

- **`check` returned 0 from an update-available branch.** The "same commit, but one of the two
  was built from a modified tree" case printed *update available* and returned `0` — and `0` is
  what every caller reads as *up to date*. The one case the dirty-tree check exists to catch
  reported success. It returns `10` now.
- **"unreachable" and "not published" were one message.** `manifest_field` made one HTTP request
  per field (four of them in `apply`, which could also see four different manifests mid-upload)
  and collapsed every failure into exit 1. It is now one request, `channel_probe`, that
  distinguishes the two — because a person fixes them differently, and the desktop now offers
  the fix for the second one.

## 5. The About screen

`wire/version.rs` no longer talks to the network. It calls `control_update`, which runs the
script. The About → UPDATES card shows:

- **Channel**, with three chips (nightly / beta / stable) that change it
- **Server**, as `scheme://host`, as configured — not as hardcoded
- **Installed**, version and git from `/opt/yantrik/BUILD`
- **Channel has**, what the channel's build is — an em dash until a check has answered
- **the result, in the updater's own words**: up to date · update available · channel 'beta' is
  not published · cannot reach releases.yantrikos.com. Four sentences where there was one.
- **Check for updates**, and **Install** — which appears only when a check said there is
  something to install, and which runs the same detached `apply` the control surface runs.

A failure can no longer render as good news. `CheckOutcome::UpToDate` is reachable only from an
explicit `result=up_to_date` on exit 0; everything else — missing updater, prose from an older
copy, a truncated read, a `result=` this build does not know, even porcelain that says current
alongside a non-zero exit — lands in an error variant carrying the script's own sentence. There
is a test that walks eight failure shapes and asserts none of them is up-to-date.

The COMPONENTS table stays. It **is** fed — `build.rs` bakes each workspace crate's version in
as `COMPONENT_*_VERSION` — but its `latest-version` / `has-update` / `is-checking` fields are
gone along with the checker that invented them. There is no honest source for a per-component
"available", because the manifest describes whole builds.

The channel picker goes flat when `update.conf` is not writable by the user the desktop runs
as, and the card then says what to type instead. A disabled control with no explanation is the
same defect as a control that does nothing.

`set_update_channel` joins the control surface at grade `sensitive`: it decides what software
the machine installs next, but nothing it writes takes effect until an `apply`. Its answer is
the channel **re-read from the file afterwards**, never the channel that was asked for.

## 6. Left open

- **`install.sh` (repo root, line ~616)** still writes `updates: {channel: beta, server:
  http://…, check_on_boot: true}` into the config it generates for a from-source install. Same
  dead keys, and over http. Outside the ownership of this change; it is a four-line deletion.
- **`stable` and `beta` have never been published to.** The channel picker will happily switch
  to either and will then honestly report "not published". That is the correct behaviour and it
  is also a thing a person can do to their machine by accident. When the pipeline starts
  publishing more than `nightly`, this stops being a trap.
- **`COMPONENT_*_GIT`** is the same value for all five components: `build.rs`'s
  `git_short_hash_at` ignores the path it is given and returns the repo HEAD. Harmless in a
  single-repo workspace, misleading if a component ever moves out of it.
