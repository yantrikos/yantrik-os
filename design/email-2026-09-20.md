# The mail app said there was no account, and nobody had ever asked

The September audit recorded that this machine had no email account configured. The whole of the
Email app's tree was the onboarding screen — "No account yet", a provider picker, eight fields and
a Sign In button — and `app.describe` agreed: `Email — no account configured`,
`has_account: false`.

It may never have been about an account at all. `email-service` is registered `autostart: false`
in `crates/yantrik-ui/src/main.rs`, nothing started it, and every call the app made failed at
connect. The app's whole account test was `list_folders_via_service()` returning `Some`, and a
connection refusal returns `None` — which the app turned into `set_has_account(false)`, which
draws that form. A dead service and an unconfigured machine were the same picture, and the picture
said the machine's fault was the one it did not have.

This is Calendar's disease, found this morning, in the app next door. `design/calendar-2026-09-20.md`
has that one.

## What was wrong

**The service was never running, and every layer swallowed the reason.** Nine `*_via_service`
wrappers all returned `Option`, so a mail server's refusal, a socket that was not there and an
empty mailbox arrived at the call sites as the same value. The call sites then did what an
`Option` invites: `let _ = mark_read_via_service(...)`, `let _ = mark_starred_via_service(...)`,
`if delete_message_via_service(&msg_id).is_some() { … }` with no else, the same for archive, and
`if let Some(results) = search_via_service(&q)` with no else. A delete the mail server refused left
the list exactly as it was and said nothing, which reads as a delete that worked. A search it
refused looked like a mailbox with no matches.

**The surface answered outcomes it had not observed.** `mark_read` answered `{"marked": row}` and
`flag` answered `{"flagged": row}` unconditionally — true of the request, silent about the
mailbox. `on_sync_emails` set "Syncing...", called the loader, and then set "Synced" whether
anything had synced, failed, or never been attempted. One handler in the file was already right:
`on_send_email` had a real else with a reason on screen, and it is the shape the rest now have.

**The onboarding form could not be submitted.** Under a comment reading `Stubs for features
requiring companion bridge or complex setup`:

```rust
app.on_save_account(|_,_,_,_,_,_,_,_| { tracing::info!("Save account (standalone mode)"); });
app.on_test_connection(|_,_,_,_,_| { tracing::info!("Test connection (standalone mode)"); });
app.on_oauth_google(|| { tracing::info!("OAuth Google (standalone mode)"); });
```

Eight fields of a filled-in form, taken and dropped. There was no path from a fresh install to a
configured account through this window — for a person or for a mind. Nine more handlers were the
same line with a different string.

**A numeric `which` searched for nothing.** `args["which"].as_str().unwrap_or_default()` gives
`""` for a JSON number, so `open_message which=1` — which is how a caller that has just read
`describe.messages` refers to a message — answered `nothing in this folder matches ""`. A caller
reads that as a search for nothing, which is not what it asked, so it retries the same call.

**And four smaller ones, found on the way.** `detail_to_ui` set `id: 0` on every message it
built, and the reading pane draws on `email-detail.id > 0`, so the detail pane never opened for
real mail at all — only for the demo fixture, which sets `id: 1`. The same function hardcoded
`is_read: true` and `is_flagged: false`, because the service fetched `FLAGS` and threw them away.
Archive was hardcoded to `[Gmail]/All Mail`, which is a folder on exactly one provider.
`SmtpTransport::relay` opens port 465 regardless of configuration, so the `smtp_port` in every
account was read from the config file and never used.

## What changed

**The service is started on demand.** Every call goes through
`yantrik_app_runtime::service::client("email")`, which asks the shell to start the service and
clears the transport's circuit breaker — the same mechanism Calendar got this morning, now with
its second caller. The budget is two seconds, because the control surface gives an action three on
the UI thread before telling the caller the app did not answer while work carries on.

**Three states, three answers.** `email.accounts` is new on the contract and it is the method that
had to exist: it answers from the config file alone, without a socket to any mail server, so
"nothing is configured" is a different answer from "the mailbox would not open", and both are
different from the service not running. `MailState` in `apps/email/src/state.rs` is the
distinction, made once:

| | on screen | `describe` |
|---|---|---|
| unreachable | a panel, not a form: "The mail service is not running", the reason, and the sentence that this is not the same as having no account | `service: "unreachable"`, `has_account: null`, `notice` |
| up, no account | the setup form, subtitle "No account yet" | `service: "up"`, `has_account: false`, and `account_store` naming the file |
| ready | the mailbox | `service: "up"`, `has_account: true` |

`has_account` is deliberately `null` and not `false` in the first row. With nothing answering, the
app has not been told whether an account exists, and `false` is the exact claim that had an audit
conclude this machine had no mail account.

**Failures are said twice.** `EmailClient` has a `notice` strip and `describe` carries the same
string. Every swallowed site reports: a delete or a move that fails says so and leaves the list
alone rather than pretending; a search that fails is a refusal rather than zero results; opening a
message that could not be marked read says that it could not.

**The actions answer what they observed.** `mark_read` and `flag` list the folder again and read
the flag back off what the mail server now says, then answer with that. `delete` and `archive`
check the message actually left the folder and report it as a failure if it did not. The sync
runs on a worker thread and says `Synced · 12 in INBOX` only when a sync returned, with the count
it returned.

**`which` takes a row number.** A number is a row number and is *not* then tried as text: "9" is
a substring of "Invoice R0093", so a caller asking for the ninth message of a folder holding three
would otherwise be handed the second one and told nothing. Out of range says how many there are.
Nothing quotes an empty string back, ever. `describe.messages` publishes each row's number beside
it, so a caller never has to count the list itself.

**The form works.** `email.test_account` tries the supplied settings against IMAP and SMTP and
reports both halves — an account whose IMAP works and whose SMTP does not can read mail and cannot
send it, and one word for both hides that. `email.save_account` signs in before it writes
anything, so an account that lands in the config file is one that worked at least once; a save
that fails leaves the form up, holding what was typed, with the mail server's own answer above it.

Both run on a worker thread. Both are bounded: there was no timeout anywhere in this service, so a
mail host that swallowed SYNs held a request for the operating system's own retry budget, and one
that completed a handshake and then stopped talking held it forever. Eight seconds on the connect
and on every read and write after it.

Failures are named rather than counted. `services/email-service/src/connect.rs` takes the library's
own words and says which of them this is: no such host, the connection was refused on port N,
timed out, a TLS error, the sign-in was rejected — with the server's own sentence after it. An
unfamiliar reply is passed through as it came, because an unfamiliar reply a person can search for
beats a familiar one that says nothing.

## The password, and what was decided about it

> **Superseded on 29 Oct 2026 (#538).** The passwords and OAuth tokens are in the credential vault now; see "The password moved into the vault" at the end of this file. What follows is the decision as it stood on 20 September.

**This is the part that needs the project owner's decision.**

The mail service reads accounts from `~/.config/yantrik/email.json`, a JSON list with a `password`
field in clear text. That is where it read them before today and it is where they are written
now. What changed is that the file and its directory are created 0600 and 0700, the service
reports `secrets_are_plaintext: true` on `email.accounts`, and the setup screen says it in plain
words under the password field:

> This password is stored in clear text in ~/.config/yantrik/email.json, readable only by you
> (mode 0600). This machine has no secret store the mail service can reach yet.

The sentence comes from the service's own answer, so the day that stops being true it stops being
said.

It is not good enough, and the alternative exists in this tree. `yantrikdb_core::vault` is
AES-256-GCM with a per-vault data key and an optional PIN, and the companion's `vault_store` /
`vault_get` tools are built on it. `crates/yantrik-ml/src/provider/secret_store.rs` is a second
one: the OS keyring through the `keyring` crate, falling back to an encrypted file where
secret-service is not running — which on this headless test machine it is not.

Reaching either from `email-service` is more than this pass and it is not a decision to make on
the way past:

* the vault lives in the companion's SQLite database, so a mail service would either link
  `yantrikdb-core` — putting the mind's database inside a network daemon — or ask the companion
  over its socket for every credential read, which makes reading mail depend on the mind being up;
* a PIN-protected vault cannot be read by a background poll with nobody at the keyboard, and what
  should happen then is a product decision, not an implementation detail;
* the keyring path needs a session secret-service that this machine does not run, so on this
  machine it would fall back to its own encrypted file with its own key on the same disk — better
  than clear text, and worth having, but a third secret store in one OS.

The honest shape is one credential service that owns this for every app, and the mail service as
its first caller. Until then: clear text at 0600, said out loud on the screen it was typed into,
and written here.

Three related rules are in force now regardless of where the secret ends up. `AccountSettings` and
the service's `Account` both have hand-written `Debug` implementations that redact the password
and the OAuth token, so a `{:?}` in a tracing line cannot print one. Every sentence built from a
mail server's reply goes through `without_secret` first, because a server is free to quote back
the line it was sent and one `LOGIN` echo would put a credential in a notice, in `describe`, and
in a mind's transcript. And **no control-surface action accepts a password**: `docs/app-control.md`
is explicit that the transcript is readable, configuring an account is a person's act at the
keyboard, and there is no version of it that belongs on that surface. `tests/email-core` builds
everything with a sentinel password and asserts it comes out of nothing.

## "Sign in with Google" was gone rather than wired — and now it is wired

*The paragraph below is the original decision. What followed it is the section after.*

There is an OAuth2 flow in this tree — `connect_service` in the companion's tool registry, backed
by `crates/yantrik-companion/src/connectors/oauth.rs`. It cannot be the one behind that button.
It mints tokens into the companion's own connector store under Gmail-API scopes
(`gmail.readonly`); IMAP XOAUTH2 needs `https://mail.google.com/`; and `email-service` reads its
token from its own config file, which nothing writes to from there. A button that completed a
flow the mail service cannot use would be a new fabricated success in place of the one being
removed, so the button is off the screen with the reason at the site. Gmail works from this form
with an App Password, which is what the provider picker explains how to get.

## The Google sign-in

The report was one sentence: *"I was not able to add the email, login using Google was not
working. Nothing happens when I click on the link."* The click did nothing because the button had
been taken off the screen that morning, for the reason above. It is back, with a flow behind it
that ends in a mailbox this service can open.

### What happens when it is clicked

`email-service` gained three methods, and it is three rather than one because there is a person in
the middle of the flow. They leave for a browser, choose an account, read a consent screen that
says *full access to Gmail*, and come back — seconds at best, minutes in practice. The app's
budget for a service call is ten seconds and the control surface's is three, so a single blocking
`sign_in_with_google` would time out on every **successful** sign-in and freeze the window for the
whole of it.

| method | takes | answers |
|---|---|---|
| `email.oauth_begin` | `{ provider: "google" }` | `{ flow_id, auth_url, expires_in_secs }` |
| `email.oauth_status` | `{ flow_id }` | `waiting` \| `done { account }` \| `failed { reason }` |
| `email.oauth_cancel` | `{ flow_id }` | `{ cancelled }` |

`oauth_begin` binds a loopback socket on a port the operating system picks — **not** a fixed one:
a fixed port is one another process can already be holding, and the failure that produces is
"Sign in with Google does nothing", which is the report this change came from. It answers in
microseconds with the consent URL, and leaves a thread on the socket with a five-minute life. A
listener left open on a desktop for an abandoned sign-in is a port accepting connections for no
reason, so the thread closes it and the flow says why.

The app opens that URL with `xdg-open`, on a worker thread, detached, and **bounded**: it waits a
second and a half for an exit code, because `xdg-open` on a machine with no handler exits non-zero
and that is the case that has to be said rather than swallowed. Still running after that is a
browser starting, which is a success from here. The child is reaped on a thread either way.

The screen then shows *Waiting for Google…*, what to do in the browser, and a Cancel that is
real — it calls `oauth_cancel`, which stops the listener within 150 ms. The Test Connection and
Sign In buttons are not drawn during the wait: both sign in with a password the form does not have
during this flow, and a control that is drawn and refused in Rust is a dead control with extra
steps.

Polling is a worker thread asking `oauth_status` once a second. Never the UI thread: the control
surface gives an action three seconds there before telling its caller the app did not answer.

### What is verified before anything is written

The same rule `save_account` follows, and for the same reason. **A token Google issued is not the
same fact as a mailbox that opened.** The scope can be wrong, the Gmail API can be disabled on the
client, IMAP can be turned off on the account. So the flow's last step before the accounts file is
an IMAP `AUTHENTICATE XOAUTH2` against `imap.gmail.com:993` with the access token, and a failure
there leaves nothing written — the app stays on the setup screen with Gmail's own answer above it.

The address is **not typed**. `openid email` is in the scope list so it comes back in the id token,
which is read (not signature-verified: it arrived in the body of a POST this process made to
`oauth2.googleapis.com` over TLS, so there is no third party between the two for a signature to
protect against). `userinfo` is the fallback. An address typed into a box and a mailbox a token
opens are two different facts, and a form that lets them disagree produces an account that signs
in as somebody else.

A sign-in that comes back **without a refresh token** is refused at the point of sign-in rather
than accepted. `access_type=offline&prompt=consent` are on the URL exactly so that cannot happen;
if it happens anyway the account would stop working within the hour, and the person would find
that out at the mailbox rather than at the button.

### PKCE, and why the companion's helper was not copied

`crates/yantrik-companion/src/connectors/oauth.rs` has a PKCE helper and it is not one to reuse:

* its `sha256_base64url` shells out to `sha256sum`, and **falls back to base64 of the verifier
  itself** when that fails. That is a valid-looking S256 challenge which is not a hash of
  anything, and a flow using it has PKCE's protection removed with no symptom at all;
* its `random_byte()` is the system clock mixed with a thread-id string length. A code verifier an
  observer of the consent URL can reconstruct is the thing PKCE exists to prevent.

`services/email-service/src/google.rs` uses `sha2` for the digest and `/dev/urandom` for the
entropy, with a **hard refusal** rather than a fallback if either is unavailable. RFC 7636's
published test vector is in `tests/email-core`, which is what catches a silent fallback.

The `state` parameter is checked before a code is believed. Any page in any browser on this
machine can `GET 127.0.0.1:<port>?code=…`; the state is the only thing that says the reply belongs
to the flow this service started. A request carrying a code under a state this service did not
issue is a named failure. A request carrying neither — a favicon, a pre-connect, a port scan — is
**ignored and the listener keeps waiting**, because a sign-in that failed because the browser was
tidy would be one that works on some browsers and not others for no findable reason.

### Tokens, and the hour

An OAuth account stores three new things beside the servers: `oauth_token` (the access token, one
hour), `oauth_refresh_token`, and `oauth_expires_at` as an absolute Unix time — absolute because it
is written to a file and read back by another process days later.

`EmailHandler::get_account` is the single chokepoint every one of the nine mail methods already
went through, and it now renews before it returns: if `needs_refresh` (expired, inside a 60-second
skew, **or unknown**) it exchanges the refresh token and writes the new access token down. Unknown
counts as expired on purpose — refreshing a token that was still good costs one HTTPS round trip;
not refreshing one that was not costs a failed sign-in that reads as a broken account. The new
token is persisted rather than held in memory, because the alternative is a token request per
click across nine methods that each open their own session.

A revoked or expired refresh token is `invalid_grant` from Google, and it is named:

> Google sign-in expired — sign in again. (Google will not renew this account's access: the
> sign-in was revoked, or it expired.)

Deliberately **not** "authentication failed". There is no password on the account and nothing in
the settings to correct; sending someone to check credentials sends them nowhere. The same applies
one layer out: `connect::name_oauth_failure` catches Gmail's `[AUTHENTICATIONFAILED]` on an OAuth
account — which the password classifier would call "the sign-in was rejected" — and says the same
sentence. Everything that is *not* an authentication failure (a host that will not resolve, a
closed port, a TLS error) is named exactly as it is for a password account, because none of that
has anything to do with how the account signs in.

**SMTP XOAUTH2 is wired too.** It was the missing half: the IMAP side had `XOAUTH2` in
`imap_session` since before this change and `smtp_transport` only ever built `Credentials` for
PLAIN/LOGIN — so an account signed in with Google could have read mail and could not have sent
any, and the sentence for that failure would have been about a password it does not have. lettre's
`Mechanism::Xoauth2` is named explicitly, because lettre's default list is PLAIN then LOGIN and
Gmail answers `535` to either with a bearer token.

### The credential, and where the client id comes from

The access and refresh tokens go into `~/.config/yantrik/email.json` beside the passwords, at the
same 0600, under the same decision recorded above — **and the refresh token is the bigger secret of
the two**: an access token is an hour of access, and a refresh token is all of it until somebody
revokes it. `secrets_are_plaintext` covers this and the screen still says so. Everything in this
change follows the three rules already in force: `Account`, `AccountSettings`, `Pkce`,
`GoogleClient` and `Tokens` all have hand-written `Debug`s that redact; `without_secrets` (the
plural of `without_secret`) clears **every** secret an account holds out of any sentence built from
a server's reply, because the XOAUTH2 line carries the access token exactly as `LOGIN` carried the
password; and no control-surface action accepts one.

Signing in with Google over an address that had an App Password **clears the password**. It is not
used for anything afterwards, and a credential kept after it stops being needed is a credential
kept for no reason.

The OAuth client id is looked for in two places, environment first:

1. `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`. `crates/yantrik-ui/src/main.rs` already sets these
   from `config.connectors.google_client_id` **before** `start_services()`, and
   `ServiceManager::start` spawns with a plain `Command::new(binary)` and no `env_clear`, so a
   service started on demand inherits them. That path was checked and works; nothing in
   `service_manager.rs` needed changing.
2. `~/.config/yantrik/google-oauth.json` — `{"google_client_id": …, "google_client_secret": …}`.
   Deliberately not `email.json`: that file is a list of accounts, the conformance probe
   fingerprints it and asserts it is untouched, and a client id is a property of the build rather
   than of an account. (`YANTRIK_GOOGLE_OAUTH_CONFIG` overrides the path, as
   `YANTRIK_EMAIL_CONFIG` does for accounts.)

An exported-but-empty `GOOGLE_CLIENT_ID` — what a shell script that read a missing key produces —
is **not** treated as configured. A `google-oauth.json` that is not there is not an error; one that
is there and broken is, for the same reason a broken `email.json` is: a typo silently read as
"nothing is configured" is how a working setup comes to look like an absent one.

### No dead control, either way

`email.accounts` now answers `google_sign_in: { available, note }` (`#[serde(default)]`, so an
older service parses as "not available", which is the truth about an older service). The setup
screen reads it before it draws anything:

* **client id configured** → the button, and under it a line naming where the client id came from.
* **no client id** → no button, and the service's own sentence in its place: *Sign in with Google
  is not available in this build: … Gmail works from this form with an App Password — Google
  Account › Security › 2-Step Verification › App passwords.* A missing button with no reason given
  is indistinguishable from a broken one, which is the fault being fixed here, one step earlier.
* **mail service unreachable** → a third sentence, because "this build has no Google client" and
  "this app cannot tell" are different claims and only one of them is fixed by setting a client id.

Failures are said twice throughout, as everything else in this app is: on the setup form the
person is looking at, and in `describe.notice` for whatever is driving the window.

### The control surface

One new action, `begin_google_sign_in`, graded **`sensitive`**. It takes no arguments — there is
nothing to parameterise, the provider is Google because the scope and the servers are, and the
address comes from the sign-in rather than from a caller.

The grade is about what it does to the person rather than to the machine. By itself it changes
nothing: no account is written, no mailbox touched, and the flow cannot complete without somebody
choosing an account and reading a consent screen. But it puts that screen in front of them,
unasked, on their own display, and a consent page a person did not go looking for is exactly the
shape of the thing they should not be trained to click through. `sensitive` sits under the default
ceiling and above a `tool_permission: standard` one. It answers `{"opened": true}` and a note
saying to ask `describe` again — not "signed in", which is decided in a browser by a person minutes
later.

`save_account` and `test_connection` remain off the surface and always will: they take a password,
and `docs/app-control.md` is explicit that the transcript a mind works in is readable.
`begin_google_sign_in` is the exception that proves that rule rather than a hole in it — it accepts
nothing, carries nothing back, and the credential it ends in never enters the app process at all.

### What the shipped ISO cannot do, and what Pranab has to do

**This has to be said plainly, because it is a constraint on shipping rather than on the code.**

`https://mail.google.com/` is a Google **restricted** scope. An OAuth client that has not been
through verification can use it, but:

* **100 test users.** Every address that signs in has to be listed on the OAuth consent screen's
  test-user list while the app is in *Testing*, and the cap is 100.
* **Refresh tokens expire in 7 days.** For a client in *Testing*, Google expires the refresh token
  after a week regardless of use. The mail service handles this correctly — `invalid_grant` becomes
  *Google sign-in expired — sign in again* — but the person signs in again every week. That is not
  a bug in this code and it cannot be fixed in this code.
* **Publishing needs verification and a security assessment.** Moving the client to *In production*
  with a restricted scope requires Google's OAuth verification (branding, a homepage, a privacy
  policy, a demo video) **and** an annual third-party CASA security assessment, which costs money
  and takes weeks.

So a shipped Yantrik OS ISO cannot carry a working Google sign-in on a Yantrik-owned client until
that verification is done. What it can carry is the code, switched off with the sentence explaining
why, and the App Password path that works today on every build. The two honest shipping options:

1. **A verified Yantrik client** — do the verification and the assessment, then bake the client id
   into the image. This is the only option that makes the button work out of the box for a stranger.
2. **The user's own client id** — each person makes a Desktop-app client in their own Google Cloud
   project, which takes about five minutes and has no verification requirement for their own
   account (they are the owner, not a third party). This is what the second config file is for.

**To create the client (option 2, and how to test option 1):**

1. <https://console.cloud.google.com/> → create a project (any name).
2. **APIs & Services → Library** → enable **Gmail API**.
3. **APIs & Services → OAuth consent screen** → External → fill in the app name and support email
   → **Add or remove scopes** → add `https://mail.google.com/` (it will be flagged *restricted*) →
   **Test users** → add the Google account that will be signing in.
4. **APIs & Services → Credentials → Create credentials → OAuth client ID → Application type:
   Desktop app.** *Desktop app*, not *Web application* — a Web client rejects a loopback redirect,
   and Google answers `redirect_uri_mismatch`, which this service names in those words.
5. Copy the client id and client secret. A Desktop client always has a secret; Google's own docs
   say it is not treated as confidential (it ships in every copy of the binary, which is why PKCE
   is there), and it is still sent because the token endpoint rejects a request that omits the
   secret of a client created with one.

**Where to put them**, either:

```bash
# ~/.config/yantrik/google-oauth.json  (created by hand; chmod 600)
{
  "google_client_id": "…apps.googleusercontent.com",
  "google_client_secret": "GOCSPX-…"
}
```

or in the shell's own config, which propagates to every service started after it:

```yaml
connectors:
  google_client_id: "…apps.googleusercontent.com"
  google_client_secret: "GOCSPX-…"
```

Either way, the Email app's setup screen changes from the "not available in this build" sentence to
a working button the next time `email.accounts` is asked — which is on every load and on Refresh.

## The other dead controls

Eleven handlers were a `tracing::info!` or an empty body. Five are real now:
`save_account`, `test_connection`, `save_draft` (an unsent message is a file, and cancelling the
composer keeps it rather than discarding it — Compose reopens it), `triage_filter` (a filter over
the rows already in hand, so switching tabs asks the mail server nothing) and `ai_classify`
(through the same `companion::ask` path the summarise and draft actions already use, with the
answer checked against the four labels the screen can draw rather than pasted into the badge).

Six are gone, each with the reason written where it stood:

* **`oauth_google`** — above, and since replaced by `sign-in-with-google`, which has a flow behind
  it. See *The Google sign-in*.
* **`download_attachment` and `preview_attachment`** — the contract's `EmailAttachment` carries a
  filename, a MIME type and a size. There is no method on this wire that returns a part's bytes,
  so neither button could ever have done anything. The chips list what the message carries, which
  is true, and stop there. The app fills them from the open message now instead of only in the
  demo fixture.
* **`set_signature`** — it read `email-signatures`, an `in` property nothing in the repository
  ever set, so the list was always empty and the block never drew. There is no signature editor
  anywhere in this app for it to have listed. `ComposeRequest.signature` is still on the wire for
  whoever builds one.
* **`back_pressed`** — an empty body, and nothing on the screen called it.
* **The Priority triage tab** — nothing in this app or on its wire says a message is important,
  and `email-priority-count` was another `in` property nothing set, so the badge never drew and
  the tab filtered on a quality no message had. Three tabs: All, Unread, Flagged.

"Add account" is real rather than removed: it opens the setup form over the mailbox, and gains a
Cancel that only exists when there is a mailbox to go back to.

## Grades

All six actions were ungraded, which is to say `standard` by default. They are graded explicitly
now, and none of them is `safe`.

| action | grade | why |
|---|---|---|
| `open_message` | standard | marks the message read on the mail server, which is a change someone else can see |
| `select_folder` | standard | looks local and is not: it asks the mail server for that folder |
| `search` | standard | changes nothing and still leaves the machine, as an IMAP SEARCH |
| `mark_read` | standard | changes a flag on the mail server |
| `flag` | standard | the same |
| `compose` | standard | fills the composer and does not send |
| `begin_google_sign_in` | sensitive | changes nothing by itself and cannot finish without a person — but it puts a *full access to Gmail* consent page on their screen, unasked |

`safe` in this OS's ladder is for something that changes nothing and stays on the machine, and
every action on this surface reaches a mail server across the network. Nothing is above
`standard` because nothing here sends or deletes mail. Anything that did would be `sensitive` at
least — mail that has gone cannot be taken back, and a deleted message is not on the server any
more — which is why `send`, `delete` and `archive` are not published, and why `compose`
deliberately drafts and stops. `save_account` and `test_connection` are not on the surface at all,
for the credential reason above.

## What is left

* **The credential store**, above. The largest thing here and the one that needs a decision — and
  a Google refresh token now sits in that same clear-text file, which raises the stakes rather than
  changing the answer.
* **Google verification, or a client id per user.** The section above has the whole of it: a
  restricted scope, 100 test users, seven-day refresh tokens, and a security assessment before a
  Yantrik-owned client can be published. Until one of those two is chosen, a shipped ISO's Email
  app says Google sign-in is unavailable and points at the App Password path. That sentence is the
  service's, so the day a client id exists it stops being said.
* **The probe does not exercise the Google sign-in.** `tests/conformance/probes/email.py` runs on a
  machine with no account and does not give it one; a real sign-in needs a browser and a person, so
  there is nothing for it to assert beyond what it could check on the surface. Two things it
  *could* check without signing in to anything, and does not yet: that `describe.actions` contains
  `begin_google_sign_in` graded `sensitive` and declaring no parameters (its existing
  "no action accepts a password" check already passes, since the action takes none), and that
  `email.accounts` answers a `google_sign_in` object whose `note` is non-empty in both the
  available and unavailable cases — the "no dead control, either way" rule, checked rather than
  asserted in prose. Neither was added here, because the probe is not this change's file.
* **The mailbox is still on the UI thread.** Only the sync, the connection test and the save run
  on a worker. Opening a folder or a message blocks the window for as long as the mail server
  takes, and the client budget was raised from two seconds — which called working mailboxes
  unreachable — to ten, which is long enough for a concurrent `app.describe` to time out at
  three while the work carries on. That is true rather than fabricated, and it is not right. The
  fix is for the mailbox to live off the UI thread entirely, which is a larger change than this.
* **This machine has two email stores.** `email-service` reads `~/.config/yantrik/email.json`;
  the built-in companion reads `EmailConfig` from its own `config.yaml` and has its own
  `imap_client` and `smtp_client` beside it. Neither reads the other, so an account added in this
  window is invisible to the mind's own email tools and the other way round. This is exactly the
  two-calendars split that was closed this morning, one domain along, and it wants the same
  answer: one owner, and the companion's tools as callers of the service's contract.
* **Attachments cannot be opened**, because the contract has no method that returns a part's
  bytes. The chips say what is there and nothing offers to open it.
* **No paging.** `list_messages` asks for page one and the app has no way to ask for page two, as
  it never had.
* **`email.search` searches INBOX** whichever folder is open, and its IMAP query interpolates the
  search text into `OR SUBJECT "…" FROM "…"` without escaping a quote. That is the service's, it
  predates today, and it was not touched.

## The password moved into the vault (29 Oct 2026, #538)

The decision above said a credential service neither process had yet was the honest shape, and
that a locked vault was a product question. Both are settled. Saved AI providers moved their keys
into the credential vault in #1015; the mail service now does the same through the same machinery
(`yantrik_foundation::vault`: `KeyVault`, `keep` with its read-back, `opened`).

**What is where.** `email.json` holds addresses, servers, ports and when an OAuth access token
stops working. It holds no secret. Each account's password and OAuth tokens are one vault entry,
`mail:<account id>`, a small JSON object. The setup form's password is typed into the Email app's
own window and goes to the service in the one `save_account` call that needs it, never through a
model turn and never through `app.act`.

**How the separate process gets the password.** The shell publishes a small door on the service
bus, `credentials` (`crates/yantrik-ui/src/credential_door`). The mail service holds a
`ShellVault` (`yantrik-service-sdk`) where the shell holds its own, and asks the door at the
moment it needs a secret: to keep one (`store`, read back), to sign in to a mail server (`value`,
for the length of the call, then dropped), to remove one. Nothing is cached and nothing is written
by the service.

Why a pull and not a push from the shell: a secret is born in the service (the form, a Google
sign-in, a renewed token), so the service needs a way to the vault whatever the direction of the
other call; with that door in place a second path that pushes from the shell would be a copy to
keep in step. It also makes "locked" the vault's own word at the moment of use, not a state this
service has to remember. The socket is mode 0600 in a 0700 directory; the door answers only a
process the kernel says is `email-service` and runs as this user (`owner::must_be_program`); the
service speaks only to a process the kernel says is the shell (`expecting_peer(must_be_the_shell)`),
so a process that bound the socket first never sees a password; and the door answers only `mail:`
ids, so it cannot read a saved provider's key or a free tier's. Same-user limits stand (#154).

**A shut vault.** Mail is not checked. `email.accounts` says `waiting_for_vault`, every call that
needs the password is refused with the one sentence "Mail is waiting for the vault. Unlock it and
mail will check again." on its own code, the Email app shows that sentence and leaves what is on
screen alone, and it asks again every five seconds until the vault is open. The shell tells the
service when the vault opens (`email.vault_opened`, from the same `opened()` hook the providers'
migration uses), and the service's migration runs again then.

**Migration.** An account an older service wrote with its password in the file is moved: the
service copies it into the vault, reads it back, and only then rewrites the file (atomically,
0600) without it. A shut or failing vault leaves the file byte for byte as it was, and the pass
runs again every minute for an hour and at each opening. `secrets_are_plaintext` is true for
exactly as long as a secret is still in the file, and the setup screen says what is true.
Using an account does the same move first, so a clear-text copy is never used in place of the
vault.

**Removing.** `email.remove_account` forgets the vault entry first and then the account; a shut
vault refuses, so a secret is not left behind by an account that has gone from the list.

**The companion is on this stack too (#1022).** It used to keep its own mail accounts in
`config.yaml` (`email.accounts`, each with its password in clear text) and ran its own IMAP and SMTP
clients with them. Those clients are gone. Every companion mail tool (`email_check`, `email_list`,
`email_read`, `email_send`, `email_reply`, `email_reply_all`, `email_forward`, `email_search`,
`email_mark_read`, `email_mark_unread`, `email_flag`, `email_unflag`, `email_delete`, `email_move`,
`email_archive`, `email_list_folders`) calls the service with the methods the Email app uses, in the
folder the message was listed from; names, arguments and permission grades are unchanged, so a send
is still a card. `email.import_account` (new, desktop programs only) brings an account in with its
secret, address as identity: an address the service has is left exactly as it is, a new one has its
secret kept in the vault and read back first. `email.mark_read` takes `message_ids` so marking a
folder read is one mailbox session, and a message summary now carries `from_address` and
`message_id` (the cache and a reply's threading need them). The companion's cache of listed mail
(`emails`) stays: the mind's message numbers and the VIP-mail playbook rest on it, and it holds no
secret.

The shell moves what an older `config.yaml` still holds (`yantrik_companion::email::legacy`, run at
start, every minute for an hour and at each vault opening): per account, the service imports it,
then the entry leaves the file; a shut or failing vault leaves the file exactly as it was. Before
the first rewrite the original is archived as `config.yaml.before-1022-<stamp>` (0600, the file's
owner), never deleted, and the person is told where it is because it holds the old password. The
rewrite is atomic and keeps the file's mode; its comments survive only in the archive.

Google Calendar sync used to borrow the mail account's OAuth tokens from `config.yaml`. The service's
Google sign-in asks for the mail scope only, so there is no calendar token to borrow, and sync is off
until a source provides one (`calendar::GoogleAccess`); the machine's own calendar is unaffected.

**Not done here.** An account deleted by editing `email.json` by hand leaves its vault entry behind,
because nothing lists the vault's mail entries; `email.remove_account` is the way.
